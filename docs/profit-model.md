# Finance planning and manual costs

## Boundaries

This is a planning tool, **not official base prices, approved driver compensation, a profitability guarantee, earned wages, payroll or a payout system**. No scenario is persisted or applied to checkout. The fixed extra-pickup platform rule is also implemented separately behind an explicit, default-disabled Stripe-test-only checkout flag; see [test checkout pricing](extra-pickup-pricing.md). Existing base fee defaults and payout flows are unchanged. No cloud operations are needed for the calculator.

- **Estimated:** hypothetical fees, paid merchant count, driver guarantee and operating costs. The UI starts with editable illustrations, including $199/merchant/month and $600/month hosting. These are not verified collections or real hosting quotations.
- **Earned:** would require independently implemented labor/contract, completed work, minimum-pay and entitlement rules. This feature creates no such records.
- **Paid:** would require independently reconciled disbursements. Manual costs do not assert money was paid, and this feature sends none.
- **Manual cost:** an administrator's expense observation. It is deliberately separate from all three statuses above and from the existing customer refund operation.

## Fixed platform fee policy and maintenance

A **fixed platform/service fee per checkout** is the simplest transparent planning option, rather than a percentage or hidden surcharge. **No fee amount or maintenance budget is approved.** The existing editable $2 service fee is illustrative, not an approved $1/$2 price or a live-rate change. The delivery fee and platform/service fee are each modeled **once per checkout**, plus separately modeled optional priority fees. There is **no second maintenance customer fee**.

Maintenance/support is a **recurring platform operating cost**, separate from customer income and worker pay. `maintenanceCents` is an optional monthly integer-cent assumption, 0 through `MaxMoney` (100,000,000 cents); omitted inputs and the UI default are zero for backward compatibility. **Zero means no approved budget, not zero actual maintenance costs.** Likewise $600 hosting is an illustration, not a quotation or cost promise. Keep support staffing in monthly payroll, and exclude overlapping payroll/other overhead from maintenance. Enter only non-overlapping maintenance contracts, upkeep or support expenses here.

Separate the three views:

- **Forecast income:** customer delivery + platform/service + expected priority fees, plus assumed merchant subscriptions, before costs; not net actual revenue or profit.
- **Worker cost estimates:** driver and shopper costs, including modeled premiums, are deductions, not implied payouts. Existing [migration 009](../db/migrations/009_priority_test_checkout.sql) priority snapshots earmark the test-only shopping/delivery surcharges for workers as allocation intentions; **allocations are not platform profit**, earned wages, payables or automatic payouts.
- **Platform operating costs:** processing excess, unrecovered refund losses and non-overlapping variable costs, plus monthly hosting + maintenance + other overhead + payroll. Subtract these once to obtain a net operating **estimate**.

The current checkout `service_fee`/`serviceFeeCents` is already the base platform fee; it does not automatically pay workers. The extra pickup platform fee is separate and counted once. Migration 011 builds all invoice lines before freezing both snapshots, preserving priority allocations and exact totals. Priority configuration remains independent, gateway checkout/payment restrictions remain blocked, and no live charge or worker payout is enabled.

## Inputs and arithmetic (USD)

Money inputs are integer cents, 0 through 100,000,000. Monthly checkout/merchant counts, bundle thousandths of a mile and bundle seconds are integers, 0 through 100,000. Checkout drops per bundle are 1 through 100. UI decimal dollar strings are converted exactly to integer cents; no floating-point money calculations. All bounded calculator result cents fit exact JavaScript integers. Ledger monthly totals are decimal integer strings because record counts can grow beyond a page.

Customer fee forecast = (delivery fee + platform/service fee + conservatively expected fast fees + extra pickup platform fee) × monthly **checkouts**. One checkout corresponds to one drop: multiple merchant orders/items do not multiply base fees, driver bases, shopper costs or checkout volume. The platform extra pickup surcharge uses its own distinct-location count per checkout, not the driver's per-bundle count. Subscriptions = assumed paid merchants × assumed monthly subscription price. Capacity and demand are unknown: merchant subscriptions alone do not establish delivery demand or achievable volume.

Driver bundle estimate = base guarantee + original pickup pay + additional pickup addon + rounded(milli-miles × cents/mile ÷ 1,000) + rounded(seconds × cents/hour ÷ 3,600). Base is **per bundle and excludes separately entered pickup pay** to avoid double counting; it is not a per-merchant payment. Include waiting in explicit distance/time. Each distance/time component rounds to the nearest cent, ties away from zero. Regular bundle estimate is amortized across checkout drops, including fractional bundles for this forecast, with monthly regular driver costs rounded **up once**, then expected fast driver premium per checkout is added. The bundle output excludes this per-checkout premium, while driver per-checkout display and monthly total include it. This is not real dispatch or an earned-compensation calculation; incomplete bundle utilization may cost more.

### Nearby pickups, separate shoppers and optional priority

- `merchandiseSubtotalCents` is optional bounded money (0–100,000,000 cents), excluding tax, tips and delivery/service/priority fees. `additionalPickupsPerCheckout` is an independent 0–100 planning count, default zero. Platform surcharge = HALF UP once on subtotal × **25 basis points (0.25%)** × extra pickups ÷ 10000. First pickup is included; count distinct pickup locations minus one, never orders. 5000 cents with one extra yields **13 cents**; 10000 cents with two extras yields **50 cents**; 5000 cents with two extras yields **25 cents**, not 26. Actual checkout currently permits at most two merchants, so its maximum is one extra; the two-extra example is calculator arithmetic, not expanded checkout eligibility. Do not reuse `additionalPickupsPerBundle` as this per-checkout count when a bundle has multiple drops.

- `originalPickupCents` is explicit original pickup pay per bundle, separate from `driverBaseCents`. `additionalPickupsPerBundle` is 0–100. Each extra pickup adds **50% of original pickup pay**, rounded half up individually: 501 cents becomes 251 cents each. Total pickup pay = original + extra count × rounded(original / 2). Zero extra pickups still includes original pickup pay; zero original produces no pickup addons regardless of count. No runtime pay entitlement is created.
- `pickupRadiusMilliMiles` is 0–500 thousandths of a mile, **metadata only**. The UI defaults to the requested 0.500-mile outer cap; **0.250 miles is the recommended initial dense-city planning target**, adjustable up to the cap. Measure every extra store from the **FIRST pickup**, never chain store-to-store radii. This input neither checks distances nor implements dispatch eligibility, and it does not alter costs. Actual mileage/waiting must still be entered separately. Omission is zero, not the UI cap.
- `shopperCentsPerCheckout` is ordinary cost for **separate people who shop and prepare orders for driver pickup**, not driver pickup pay. It is per checkout, not an automatic shopper attached to every pickup. Do not enter this cost again in other variable expenses or monthly staff payroll.
- `fastServiceAdoptionBasisPoints` is 0–10000 (100 = 1%), a hypothetical uptake forecast for optional customer-selected fast shopping/delivery priority. This version models combined uptake, not separate shopping/delivery adoption cohorts. `fastShoppingFeeCents` and `fastDeliveryFeeCents` are explicit additional customer fees; `fastShopperPremiumCents` and `fastDriverPremiumCents` are explicit additional costs, all **per opted-in checkout**. The planner does not implement or configure checkout selection, fee collection, work assignment or speed promises; the repository's existing test-only priority checkout is separate and unchanged. All new money inputs and uptake start at **zero**, not suggested prices; omitted extension inputs preserve old results.

For uptake A, set E = floor((fast shopping fee + fast delivery fee) × A / 10000), P = ceil(fast driver premium × A / 10000), and H = ceil(fast shopper premium × A / 10000), **per checkout before monthly multiplication**. Each of these three weighted amounts differs from the unrounded expectation by less than one cent per checkout, deliberately understating revenue and overstating costs. This is not aggregate-only rounding or an exact fractional-adoption expectation. At 0% uptake all fast forecasts are zero; at 100% they equal the explicit fees/premiums exactly. At 33.33% uptake, combined fees of 501 cents forecast 166 cents/checkout, shopper premium 101 forecasts 34, and driver premium 103 forecasts 35. These are arithmetic illustrations, not rate recommendations.

Let F = delivery + service + E + extra pickup platform fee cents; V = processing excess + refund loss + other variable cents; B = regular driver bundle estimate including pickups; C = ordinary shopper + H cents; P = expected fast driver premium; D = drops per bundle; Q = monthly checkouts; S = subscription forecast; K = monthly hosting + maintenance + other overhead + staff payroll.

- Exact contribution/checkout **under this conservative forecast policy** = ((F − V − C − P) × D − B) / D. Rounded per-checkout displays do not drive monthly math or break-even; bundle amortization remains rational.
- Monthly driver = ceil(B × Q / D) + P × Q; monthly shopper = C × Q; monthly fast revenue = E × Q.
- Monthly contribution = (F − V) × Q − monthly driver − monthly shopper.
- Net operating estimate = monthly contribution + S − K.
- Break-even checkouts = ceil(max(0, K − S) × D / ((F − V − C − P) × D − B)), **only when exact delivery contribution under the conservative policy is positive**. This is the smallest count with calculated net ≥ 0: all non-bundle monthly terms are integer cents, so net = floor(contribution numerator × Q / D) + S − K. Otherwise there is no delivery-volume break-even, even if subscriptions offset fixed costs. Zero required checkouts means assumed subscriptions already cover fixed costs; more loss-making deliveries still worsen the result. Break-even may exceed the allowed scenario volume; it does not establish achievable demand.
- Net operating margin denominator = **forecast customer fees including expected fast fees + assumed subscriptions**. Merchandise, sales tax and tips are pass-throughs and excluded. The server returns nearest integer basis points (100 basis points = 1%); zero forecast revenue produces an undefined/null margin. This is a scenario ratio, not a generic percentage of gross basket value.

The response exposes extra pickup amount, extra-only addon, original-plus-extra bundle pickup total, separate shopper costs and fast monthly forecasts. `platformServiceFeesMonthCents` = `serviceFeeCents` × checkouts and `deliveryFeesMonthCents` = `deliveryFeeCents` × checkouts; both are **already included** in `customerFeesMonthCents`, not additional fees or revenue. `maintenanceMonthCents` = `maintenanceCents` is a display breakdown **already included** in `fixedMonthCents`. Maintenance affects net and subscription-offset break-even, not checkout fees or contribution. Pickup outputs are already included in regular driver cost; fast driver/shopper premium outputs are already included in their respective monthly totals; fast revenue is already included in customer fees. Do not add breakdowns to totals again.

Processing inputs must be only the platform-borne excess **after existing merchant processing allocation**, not the entire Stripe fee again. Refund losses are unrecovered platform costs, not gross refunds including returned merchandise/tax or already reversed merchant funds. Other manual variable/overhead/payroll costs must not overlap these inputs. Staff payroll should include employer taxes, benefits and other employment costs as appropriate; do not count modeled driver labor twice. Subscription processing excess may be included as monthly overhead if applicable.

### Illustration, not a rate recommendation

$6 delivery + $2 service − $5 driver per one-drop bundle = **$3 contribution per checkout**, before processing excess, refund losses or other variable costs. At 1,000 checkouts and $600 hosting, with no assumed subscriptions or other costs, the scenario estimates $2,400 net operating result and 200 break-even checkouts. Four assumed $199 subscriptions produce $796/month and could cover $600 fixed hosting with no deliveries and no delivery losses. Real staffing, insurance, taxes, support, driver operating costs, acquisition, disputes, vehicle costs, utilization and hosting may make this unprofitable. No best payout or final rates have been approved.

## Driver retention and compliance gates

A predictable base plus explicit distance/time can be evaluated for retention, including waiting, deadhead mileage, vehicle expenses and bundle utilization. It must be tested against local minimum pay, overtime, reimbursement, scheduling and worker-classification rules **before setting any compensation**. Contractors and employees need different compliant accounting and payment processes. Future Connect driver transfers would be appropriate only for genuinely compliant contractor arrangements; employees need a separate compliant payroll system. This tool implements neither. Tips should pass through separately and should not subsidize assumed platform contribution; tip handling is currently unimplemented here.

If the proposed separate shopper workforce includes teenagers, obtain jurisdiction-specific youth-employment review **before launch**, including minimum ages, permitted hours/school-day limits, task restrictions, supervision, work permits and applicable verification requirements. No minor hiring, recruitment, age verification or employment workflow is implemented. Teen shopper plans must exclude alcohol, tobacco and hazardous tasks. Optional priority must not create safety-compromising speed promises or guaranteed delivery times; lawful hours, safe work and customer/worker protections take precedence over forecast premiums.

## Admin API and manual ledger

All routes require existing authenticated gateway admin identity and a nonempty trusted actor. Gateway policies are exact and deny by default; POST bodies are limited to 8 KiB. Never send the internal service token from the browser. Gateway URL and user session token are held in memory only; no secrets in localStorage.

- POST `/admin/finance/scenarios`: strict bounded JSON inputs; pure calculator works without a database. Omitted inputs are zero except required positive `dropsPerBundle`.
- POST `/admin/finance/costs`: `{period, category, amountCents}` plus UUID `Idempotency-Key`. Record ID is that UUID; timestamp and actor come from the server. Categories: driver, staff, hosting, processing_excess, refund_loss, other. Use existing **other** for maintenance/support expenses and **staff** for support staffing or manual shopper expense observations; no new category or migration is needed. Avoid double counting maintenance, other overhead and payroll. Zero is allowed; negative costs, wage approvals and paid status are not.
- GET `/admin/finance/costs?period=YYYY-MM&limit=50&offset=0`: UTC accounting period 2000–2100; limit 1–100; offset 0–100,000. One query snapshot returns whole-month total plus a timestamp/UUID-ordered page. This is not a revenue or paid-cost reconciliation report.

Identical UUID + actor + payload retries return the same record. Differing actor or payload returns 409. Retain the key after a network error; changing the form creates a new key and may create another expense. Review existing records first. Records are append-only; update/delete/truncate are rejected. This first version has no correction/reversal workflow, attachment storage, payroll assertions or automatic import into scenarios. Refund-loss entries do not execute refunds. Production retention and access policies require operator review; there is no automatic purge.

Apply [migration 008](../db/migrations/008_finance_costs.sql) through the existing reviewed migration process before using the manual ledger. The optional `FinanceRepository` leaves existing repository mocks/implementations unchanged; unsupported repositories or missing migration return 503. Migration grants **nothing to PUBLIC**, uses invoker security, and creates no broad mutation role. A dedicated API database role needs SELECT/INSERT on `finance_costs` and EXECUTE on `record_finance_cost(uuid,text,text,text,bigint)`; no UPDATE/DELETE/TRUNCATE. Database owners can bypass protections and must be restricted operationally. Do not treat the disposable SQL test runner as a production migration command.

## Validation

Extension tests cover omitted/zero maintenance compatibility, nonnegative/maximum maintenance validation, unchanged contribution, maintenance-adjusted net and subscription-offset break-even, included-once service/delivery/priority/extra-pickup fee breakdowns, odd-cent driver pickup half-up rounding, aggregate-only platform surcharge rounding, separate checkout/bundle scopes, zero/extra pickups, separate shopper costs, radius metadata, fast 0%/100% and fractional conservative forecasts, maximum integer safety, and exact minimum break-even with subscriptions and rounded bundle costs. UI tests also cover exact decimal money, default assumptions, decimal miles, extension bounds and Go/OpenAPI/SQL source parity. Existing gateway route policies are unchanged; migration 011 adds independently gated test checkout pricing, not a production activation.

Calculator and API tests cover bounds, rounding, fractional bundle amortization, subscriptions, undefined margin, nonpositive contribution, actor/role authentication, ledger conflicts and unavailable storage. Gateway tests cover exact admin routes and body caps. UI input tests cover exact cents, invalid decimal/exponent inputs, bounds and trusted URL validation. SQL fixtures run in BEGIN/ROLLBACK and assert idempotency, nonnegative costs, append-only behavior and no PUBLIC privileges. CI applies migrations 001–011 transactionally on a fresh disposable PostGIS database before fixtures and runs the frontend finance input tests. Opt-in Go repository tests check real function calls and committed quote/ledger behavior; they refuse nonlocal or differently named database/users and are skipped without their disposable test DSNs. Offline SQL runner tests are not SQL correctness validation. No production database is migrated automatically.
